## Riwayat Edit (Transaksi & Pelanggan Paket)

Setiap kali transaksi biasa (`editTransaction()`) atau data pelanggan
Paket Bulanan/Tempo (`editSubscription()`) diedit lalu disimpan ulang,
perubahannya dicatat — siapa yang mengedit, kapan, dan field apa saja
yang berubah (dari → ke). Bisa dilihat lewat tombol "🕘 Riwayat" — di
kartu Riwayat (sebaris Edit/Hapus, khusus tampilan pemilik) untuk
transaksi, dan di modal Detail Paket (sebaris Edit Pelanggan/Hapus)
untuk pelanggan paket.

Satu tabel generik dipakai bareng oleh semua entitas yang dilacak
(`entity_type` + `entity_id`), supaya tidak perlu bikin tabel & RLS
policy terpisah tiap kali ada entitas baru yang mau ditambah riwayatnya.
Butuh tabel baru — jalankan sekali di Supabase SQL Editor:

```sql
create table if not exists edit_log (
  id bigint generated by default as identity primary key,
  owner_id uuid not null references auth.users(id),
  entity_type text not null,
  entity_id text not null,
  edited_by uuid not null references auth.users(id),
  editor_nama text not null,
  edited_at timestamptz not null default now(),
  changes jsonb not null
);

alter table edit_log enable row level security;

create policy "Pemilik & kasir toko bisa akses riwayat edit toko"
on edit_log
for all
using (
  owner_id = auth.uid()
  or owner_id in (
    select owner_id from team_members
    where member_id = auth.uid() and status = 'aktif'
  )
)
with check (
  owner_id = auth.uid()
  or owner_id in (
    select owner_id from team_members
    where member_id = auth.uid() and status = 'aktif'
  )
);

create index if not exists edit_log_entity_idx on edit_log(entity_type, entity_id);
```

Aman dijalankan kapan saja — kalau tabelnya belum ada, `logEditHistory()`
gagal diam-diam (edit datanya sendiri tetap berhasil normal, cuma
riwayatnya tidak tercatat) dan `openEditHistory()` menampilkan pesan
"belum dimigrasi" alih-alih error. `editor_nama` diisi "Pemilik" kalau
yang mengedit pemilik toko, atau nama kasir (`employeeName`) kalau
kasir. Cuma field yang BENAR-BENAR berubah yang dicatat (lewat
`diffTransactionFields()`/`diffSubscriptionFields()`) — bukan snapshot
penuh tiap kali disimpan, supaya riwayatnya ringkas dan gampang dibaca.

> Kalau sempat menjalankan migrasi `transaction_edit_log` dari versi
> sebelumnya (sebelum tabelnya digeneralisasi jadi `edit_log`), aman
> dihapus — belum ada baris nyata yang bergantung padanya:
> `drop table if exists transaction_edit_log;`

**Dua entitas SENGAJA tidak dilacak:**
- **Pengeluaran** — tidak ada tracking karena memang tidak ada fitur
  edit pengeluaran sama sekali (cuma tambah/hapus), jadi tidak ada yang
  perlu dicatat.
- **Katalog** (layanan & pengeluaran) — daftar harga/template, bukan
  catatan keuangan per pelanggan, jadi nilai akuntabilitasnya jauh lebih
  rendah dibanding transaksi & pelanggan paket. Bisa ditambahkan kalau
  ternyata dibutuhkan.


## Catatan (buku catatan bebas seputar laundry)

Tombol "Keluar" di appbar diganti jadi tombol "Catatan" (📔✏️) — tombol
Keluar dipindah ke Pengaturan → Keamanan Akun (di bawah form ganti
email/password). Fitur Catatan membuka buku catatan bebas (bukan bagian
dari sistem transaksi) untuk mencatat apa saja seputar laundry (stok
deterjen, ide promo, dll) — ditampilkan sebagai grid sampul buku
berwarna, tiap sampul menunjukkan judul + tanggal dibuat + tanggal
terakhir diedit.

Butuh tabel baru — jalankan sekali di Supabase SQL Editor:

```sql
create table if not exists notes (
  id bigint generated by default as identity primary key,
  user_id uuid not null references auth.users(id),
  judul text not null default 'Tanpa Judul',
  isi text,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);

alter table notes enable row level security;

create policy "Pemilik & kasir toko bisa akses catatan toko"
on notes
for all
using (
  user_id = auth.uid()
  or user_id in (
    select owner_id from team_members
    where member_id = auth.uid() and status = 'aktif'
  )
)
with check (
  user_id = auth.uid()
  or user_id in (
    select owner_id from team_members
    where member_id = auth.uid() and status = 'aktif'
  )
);
```

Aman dijalankan kapan saja — kalau tabelnya belum ada, `loadNotesFromDB()`
diam-diam gagal dan grid Catatan tampil kosong (bisa dibuka, tapi belum
bisa menyimpan sampai migrasi ini dijalankan), tidak memengaruhi fitur
lain.

## Nomor Nota (kode transaksi) berbasis database

Sebelumnya nomor nota (`LND-0001`, `LND-0002`, dst.) dibuat dari **panjang
array transaksi di memori** (`transactions.length + 1`) — ini berisiko
menghasilkan **nomor kembar** (dua transaksi berbeda punya kode sama):
kalau ada transaksi lama yang dihapus permanen (bukan lewat "Urungkan"),
atau kalau 2 kasir/perangkat menyimpan transaksi hampir bersamaan (race
condition), keduanya bisa menghitung nomor berikutnya yang sama sebelum
salah satu selesai tersimpan. Nomor nota yang unik & urut adalah syarat
dasar pembukuan yang bisa diaudit, jadi ini diperbaiki dengan memindahkan
penomoran ke **sequence di database** — dijamin unik meski diakses
bersamaan dari banyak perangkat.

Jalankan sekali di Supabase SQL Editor:

```sql
create sequence if not exists transactions_kode_seq;

-- Lanjutkan dari nomor terbesar yang sudah ada (aman untuk toko yang sudah
-- punya banyak transaksi lama), atau mulai dari 1 kalau belum ada transaksi.
select setval(
  'transactions_kode_seq',
  coalesce(
    (select max(substring(kode from '[0-9]+$')::bigint) from transactions where kode ~ '^LND-[0-9]+$'),
    0
  )
);

create or replace function next_transaction_kode()
returns text
language sql
security definer
set search_path = public
as $$
  select 'LND-' || lpad(nextval('transactions_kode_seq')::text, 4, '0');
$$;

grant execute on function next_transaction_kode() to authenticated;
```

Aman dijalankan kapan saja — kalau migrasi ini belum dijalankan,
`nextKode()` otomatis balik ke cara lama (panjang array) supaya app tetap
bisa dipakai, TAPI risiko nomor kembar di atas tetap ada sampai migrasi
ini benar-benar dijalankan. Jalankan migrasi ini **sesegera mungkin**.


## Navigasi PageUp/PageDown (atas-bawah) & Home/End (kanan-kiri) di form Transaksi Baru (17 Oktober 2026)

Permintaan user: selain Enter (sudah ada, lihat perbaikan sebelumnya),
tambahkan PageUp/PageDown/Home/End sebagai tombol navigasi antar kolom
form Transaksi Baru, supaya kasir dengan keyboard eksternal/numpad bisa
lompat ke kolom mana pun tanpa harus urut lewat Enter satu-satu.

Ditambahkan `TRX_FORM_GRID` (`js/12-transaksi.js`) — array 2 dimensi
yang memetakan ID tiap kolom ke posisi baris/kolom sesuai **tata letak
visual** form (cocokkan dengan `.row2`/`.item-row` di `index.html`):

```js
[
  ['inNama'],
  ['inHP'],
  ['inTanggal','inEstimasi'],
  ['itNama','itQty','itSatuan','itHarga'],
  ['inDiskon','inDP'],
  ['inStatus'],
  ['inCatatan'],
]
```

`trxGridKeyNav()` dipasang sebagai listener `keydown` di semua kolom
itu: Home/End pindah fokus ke kolom kiri/kanan DALAM baris yang sama
(diam kalau sudah di ujung), PageUp/PageDown pindah ke kolom dengan
INDEX YANG SAMA di baris atas/bawah, di-clamp ke kolom terakhir kalau
baris tujuan lebih pendek (mis. dari `itHarga` — index kolom 3 — ke
baris Diskon/DP yang cuma 2 kolom, jatuh di `inDP`).

**Trade-off yang disengaja** (disampaikan ke user): Home/End SELALU
langsung pindah fokus, TIDAK dicek posisi kursor teks dulu — jadi di
kolom Catatan (satu-satunya `<textarea>`, bisa berisi teks panjang),
Home/End tidak lagi bisa dipakai untuk menggeser kursor ke
awal/akhir teks saat mengedit, cuma untuk pindah kolom. Dipilih supaya
perilakunya KONSISTEN di semua kolom (tidak ada kolom yang "kadang jadi
navigasi, kadang tidak" tergantung posisi kursor) — kalau user merasa
ini mengganggu pengeditan Catatan panjang, perlu direvisi jadi
"Home/End cuma pindah kolom KALAU kursor sudah di ujung teks, kalau
belum biarkan geser kursor dulu" (lebih kompleks, belum dikerjakan).

Catatan implementasi: PageUp/PageUp TIDAK "mengingat" kolom asal lintas
baris berbeda panjang — index kolom yang dipindahkan selalu index
TUJUAN SAAT INI, bukan index sebelum di-clamp. Jadi PageDown dari
`itHarga` (index 3) ke `inDP` (ter-clamp ke index 1), lalu PageUp balik
dari `inDP` (index 1) akan jatuh ke `itQty` (index 1 di baris Layanan),
BUKAN balik ke `itHarga` — ini perilaku grid yang disengaja/konsisten,
bukan bug.

Verifikasi: `node --check` lulus, suite Playwright penuh (207 langkah,
0 FAIL) termasuk test baru untuk Home/End dalam baris 2 & 4 kolom,
PageUp/PageDown menyusuri semua 7 baris, perilaku clamp kolom, dan
batas atas/bawah/kiri/kanan (diam, tidak error) di baris/kolom
pertama/terakhir.

## Navigasi ArrowUp/ArrowDown + Enter di SEMUA dropdown saran/autocomplete (17 Oktober 2026)

Permintaan user: tombol Up/Down buat menggulir pilihan di "setiap menu
yang ada dropdown atau pilihan katalog", Enter buat pilih. App ini punya
2 jenis "dropdown": `<select>` native (sudah otomatis dukung Up/Down+Enter
dari browser, tidak perlu disentuh) dan dropdown saran/autocomplete
custom (`.suggest-dropdown`/`.suggest-item`, dibangun manual lewat
`<div>` + `onmousedown`) — SAMA SEKALI belum ada navigasi keyboard
sebelum ini, cuma bisa diklik/disentuh. Ada 7 dropdown jenis ini: saran
nama pelanggan (`inNama`+`subsNama`, dipakai bareng lewat
`showContactSuggest()`), saran layanan katalog (`itNama`), saran layanan
tambahan Tempo/Paket (`extraLayanan`), saran nama & kategori pengeluaran
(`expNama`/`expKategori`), saran nama Rekap Pelanggan (`rekapNamaInput`).

Ditambahkan 1 fungsi generik `attachSuggestKeyNav(inputId, boxId)`
(`js/00-globals.js`, modul paling awal dimuat) yang dipasang SEKALI di
top-level tiap modul pemilik widget-nya (`js/07-katalog.js`,
`js/08-paket.js`, `js/11-kontak.js`, `js/14-pengeluaran.js`,
`js/22-rekap-pelanggan.js`) — BUKAN di dalam `showXxxSuggest()` sendiri,
supaya listener-nya tidak menumpuk ganda setiap kali fungsi itu dipanggil
ulang tiap user mengetik (ditandai idempoten lewat `input.dataset.suggestNavBound`).

- **ArrowUp/ArrowDown** menyorot item (pakai ulang class CSS
  `.suggest-item.hover` yang SUDAH ADA di `index.html` sejak awal tapi
  sebelumnya tidak pernah dipasang JS mana pun — bukan style baru),
  wrap ke ujung satunya kalau sudah di item pertama/terakhir.
- **Enter** memicu `onmousedown` BAWAAN item yang disorot (bukan menulis
  ulang logic pilih — tiap `showXxxSuggest()` sudah memasang
  `onmousedown` yang langsung memanggil `selectXxxSuggest(...)` dengan
  argumen yang sudah benar per widget, generik ini cuma memanggil
  fungsi itu lewat `items[idx].onmousedown({preventDefault(){}})`).
  Kalau belum ada yang disorot (user belum tekan Arrow), Enter
  dibiarkan jalan seperti biasa (pindah kolom/tambah item via
  `focusOnEnter()`), TIDAK diam-diam memilih saran pertama.
- **Escape** menutup dropdown-nya.

**Konflik Enter dengan `focusOnEnter()`/`TRX_FORM_GRID`** (khusus
`#inNama`/`#itNama`, satu-satunya kolom yang punya KEDUANYA — saran
otomatis DAN navigasi Enter-pindah-kolom dari perbaikan sebelumnya):
`attachSuggestKeyNav()` SENGAJA didefinisikan di `js/00-globals.js`
(modul paling awal) dan DIPANGGIL di `js/07-katalog.js`/`js/11-kontak.js`
(dimuat SEBELUM `js/12-transaksi.js` yang memasang `focusOnEnter()`) —
urutan `<script src="...">` menentukan urutan listener `keydown`
terdaftar di elemen yang sama, dan browser menjalankan listener sesuai
urutan pendaftaran. Dengan listener ini terdaftar LEBIH DULU, dia bisa
`e.stopImmediatePropagation()` untuk mencegah `focusOnEnter()` ikut
jalan SAAT Enter benar-benar dipakai memilih saran (ada item disorot) —
tapi membiarkan `focusOnEnter()` tetap jalan normal saat Enter dipakai
tanpa menyorot apa pun dulu. Kalau urutan modul ini berubah di
`index.html`, perilaku ini bisa rusak diam-diam — jangan pindahkan
`js/12-transaksi.js` ke atas `js/07-katalog.js`/`js/11-kontak.js`.

Verifikasi: `node --check` lulus, suite Playwright penuh (208 langkah,
0 FAIL) termasuk test baru di 2 widget berbeda (`#itNama` — kasus
konflik Enter paling rawan; `#expKategori` — pola index, file
berbeda, buktikan genericity) menutupi ArrowDown/ArrowUp (termasuk
wrap), Enter dengan & tanpa item disorot, Escape, dan isi field yang
benar setelah dipilih.
